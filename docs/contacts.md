# The contact directory

`data/contacts.json` is a flat list Aigentik builds and maintains itself. Every inbound email or text either matches an existing contact (by normalized phone number, normalized email, name, or alias) or creates a new one automatically. Each contact tracks: name, any known aliases, phone numbers, email addresses, a home/mailing address, a free-text relationship label ("boss", "wife"), a type (`person`/`business`/`subcontractor`/`unknown`), standing instructions, a reply behavior (`auto` / `always` / `never` / `review`), where it came from (`email`, `sms`, `android_contacts`, or `auto`), first-seen/last-contact timestamps, a running contact count, and up to the last 50 history entries.

`sync contacts` merges in your actual Android address book (via `termux-contact-list`) without ever overwriting data Aigentik has already learned — it only fills in a name if one's missing, and adds phone numbers/aliases it doesn't already have. This only applies in Termux — see [Termux vs. Linux](installation.md#termux-vs-linux).

Reply behavior per contact overrides the general rule engine: setting someone to `never` stops all processing for them outright (still logged, no reply, no queue item); `always` skips the rule engine and auto-replies unconditionally. See [Rule engines](rules.md) for how the general (non-per-contact) rules work, and [Owner command reference](commands.md) for how to set instructions on a contact conversationally.

Every appointment is also linked to a contact record — see [Appointment scheduling](scheduling.md) for how that's used to resolve reschedule/cancel requests and to fill in the customer details on booking notifications.

**Subcontractor applications.** A "New Form Submission (Subcontractor Application)" lead-form email (or any email whose subject/body identifies itself as one — see `subcontractor-form.js`) is recognized before the normal auto-reply/scheduling flow, exactly like a Google Voice text or a calendar RSVP is. The fixed `LABEL: value` layout (business name, trade specialty, principal name, phone/email, license and GL/WC insurance status, crew tools/size, weekly capacity, references, terms agreement) is parsed deterministically — a label/synonym lookup, not an LLM call, for the same reason `calendar.js` keeps date math out of the model: it's a structured form, and a regex parser is both cheaper and more reliable than a model guess, while still tolerating label wording/casing differences between form vendors (`SC PHONE` / `Phone Number` / `phone`, `HAS LICENSE` / `Licensed`, `Yes`/`On`/`Y` for a checked box, etc). Free-text references are split on newlines/`;`, with any phone number or email address in each chunk pulled out via regex.

The applicant is saved as a contact with `type: "subcontractor"` (never `person`) plus `business_name`, `trade` (a canonical slug — see `trades.js` — recognizing synonyms like "electrician" → `electrical`, "plumber" → `plumbing`), `trade_raw` (the exact text they submitted), `licensed`/`license_number`, `gl_insurance`/`wc_insurance`, `has_tools`, `crew_size`, `weekly_capacity`, and `references` (each `{raw, name, phone, email}`). Aigentik replies with a subcontractor-specific acknowledgment (`llama.generateSubcontractorAck`) — a distinct prompt from the customer auto-reply, which never promises work or a timeline — and separately emails the admin the full parsed application. Say `list my plumbers` (or any trade) to get every subcontractor on file for that trade, or "I don't have any ... on file" if there are none; this same trade/license/insurance/crew block is appended automatically whenever a subcontractor's contact info comes up elsewhere too — `find [name]`, and the admin notification for any appointment/invite booked with them.
